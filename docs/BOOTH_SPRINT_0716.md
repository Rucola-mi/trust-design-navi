## 2. なぜ関係性マップが最優先か

ブースで見せたい体験（BOOTH_ENTRY_FORM.md）は4つ：

1. 6テーマ診断 → リテラシーマップ　→ ✅ 動く
2. 優先テーマ → AIナビ対話　→ ✅ 動く
3. **関係性マップに「家族＋家族以外（士業・友人・地域）」を配置** → ❌ **現状は血縁のみで、この体験ができない**
4. 既存サービスとの違いを5分で説明 → 3が動いてこそ説得力が出る

「家族以外も託し先になる」は TDN の差別化のど真ん中（VPC「託す」レイヤー、テーマ4とも連動）。これが画面で見せられないと、ブースの説明が「口頭の構想」になってしまう。

### 設計方針：家系図は分離し、関係性マップの1ブランチにする（2026-07-04 決定）

当初案（家系図にカテゴリを混ぜ込む Task 8）は採らない。理由：家系図は**法定相続人・代襲相続に直結する法的レイヤー**であり、単独で切り出せる状態（印刷して士業へそのまま渡せる）を維持すべきだから。加えて `family.js` の続柄計算・代襲相続判定は CLAUDE.md の要注意領域で、展示直前に触るリスクが大きい。

採用する構成（**ハブ＆ブランチ**）：

```
        関係性マップ（新ビュー view-network）
                    ┌─ 親族関係 ──▶ 既存の家系図ビューへ（無変更・単独完結）
                    ├─ 友人
        本人 ───────┼─ 士業（行政書士・FP・弁護士）
                    ├─ 医療・介護
                    ├─ 地域・行政
                    └─ サービス事業者
```

- **親族関係ブランチ**：家系図のサマリー（登録人数等）を表示し、「家系図を開く」で既存ビューへ遷移。家系図＝「相続の法的な地図」として独立
- **他ブランチ**：続柄計算が不要なシンプル人物カード（名前・役割メモ・カテゴリ色）。関係性マップ＝「意思を託す実務の地図」
- **データも分離**：家族以外の人物は `family_trees` に混ぜず、localStorage（将来 `user_records` type='network'）に別管理
- 将来の安心デザインカード（Tier 3）は、両レイヤーを1枚に合成する位置づけ

副次効果：**`family.js` を一切変更しないため、リグレッションリスクがほぼゼロ**になり、検証工数も大幅に減る。

## 3. 優先順位と作業計画
