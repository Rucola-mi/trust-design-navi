# Trust Design Navi — コードベース監査 & v7.5 改修プラン

## 概要

このドキュメントは、現行デプロイ（[trust-design-navi.vercel.app](https://trust-design-navi.vercel.app/)）のコードベース現状把握と、[VPC_v7.5.md](VPC_v7.5.md) で定義したピボット方向への改修プランを記録するものである。判断軸は [MANIFESTO.md](MANIFESTO.md) を参照。

---

## アーキテクチャ概観

### 構成

- **Vanilla JS の SPA**（ビルドステップなし、フレームワーク非依存）
- **5ビュー**を `index.html` 内で切替：LP / Diagnosis / Result / Chat / Family
- **状態管理**：モジュールレベルの `state` オブジェクト、`window.TDN.state` で跨ぎ共有
- **クラウド**：Supabase + RLS（行レベルセキュリティ）
- **認証**：Email/Password、Magic Link（OTP）両対応

### ファイル構成

| ファイル | 行数 | 役割 |
|---|---|---|
| `index.html` | 624 | LP・診断・結果・チャット・家系図の全ビュー、モーダル |
| `app.js` | 712 | 10テーマデータ、診断ロジック、結果表示、AIチャットモック |
| `auth.js` | 268 | Supabase認証、ログインUI、共有招待UI |
| `db.js` | 187 | family_trees / tree_shares のCRUD、共有ツリー読込 |
| `family.js` | 868 | 家系図全機能（描画・レイアウト・人物管理・代襲相続判定・続柄計算・印刷） |
| `style.css` | 1485 | デザイン全体（sage/peach/cream パレット） |
| `supabase-config.js` | 26 | クライアント初期化 |
| `supabase/schema.sql` | 104 | DBスキーマ、RLSポリシー |

### データモデル（Supabase）

```
family_trees(id, owner_id, title, data jsonb, updated_at, created_at)
  └── data = { persons: [...], rootId: "..." }

tree_shares(id, tree_id, shared_email, created_at)
```

RLS設計は堅実：
- `is_tree_owner()`, `is_tree_shared_with_me()` を `SECURITY DEFINER` 関数化することで、ポリシー間の無限再帰（42P17）を回避
- オーナーは自由、共有先は閲覧のみ

### 永続化の現状

| データ | 保存先 | 状態 |
|---|---|---|
| 家系図 | Supabase（ログイン時）/ localStorage（未ログイン時） | ✓ 動作中 |
| 診断結果 | メモリのみ（state.answers） | ✗ 保存していない |
| チャット履歴 | メモリのみ | ✗ 保存していない |
| 優先テーマ | メモリのみ | ✗ 保存していない |

## 強み（残すべきもの）

1. **クラウド連携が既に動いている**。家系図の保存・共有・RLSまで完結している
2. **無依存（vanilla JS）で改造しやすい**。ビルドステップなし＝Vercel即時反映
3. **5ビューSPAのフレームが汎用的**。新ビュー追加・既存ビュー改修が容易
4. **デザイン言語（sage/peach/cream）が確立**。ブランドトーン強い、v7.5マニフェストとも整合
5. **家系図エンジンが本格的**。代襲相続マーカー、続柄自動算出、印刷PDF出力まで完備
6. **3レイヤーの骨格（学ぶ／決める／託す）が既に組まれている**。v7.5でもこのまま使える

## ギャップ分析（v7.5 で必要なもの vs 現状）

### A. データモデルの拡張が必要

現在は `family_trees` のみ。v7.5では以下を保存する必要：

- 診断結果（履歴）
- デジタル遺品リスト
- SNS死後対応設定
- クリプト託しメモ（※暗号化必須／本体直保存はしない）
- 任意後見・死後事務委任メモ
- 関係性マップ（家族＋友人＋士業＋地域＋サービス）

**選択肢A**：`user_records(id, user_id, type, data jsonb)` の汎用テーブルを追加（推奨）
**選択肢B**：`family_trees` を `user_documents` にリネーム、`type` カラム追加

### B. 10テーマの拡張／差別化テーマの新設

現行10テーマは終活の伝統領域（医療・介護・相続中心）に偏っており、**v7.5の差別化テーマが弱い**。

提案：
- **テーマ11: デジタル資産・SNS・暗号資産**（新設・差別化の刃）
- **テーマ12: 家族以外の支援（任意後見・死後事務委任・見守り）**（新設・差別化の刃）

または、既存テーマ内に「デジタル」「家族以外」のサブセクションを織り込む案もある（破壊的変更を避けたい場合）。

### C. 「家系図」→「関係性マップ」へのリブランド

現実装は血縁中心。v7.5では：
- カテゴリ追加：家族／親族／**友人**／**士業（行政書士・FP・弁護士）**／**医療・介護**／**行政・地域**／**サービス事業者**
- 代襲相続マーカーは**オプション化**（家族関係の一側面として、ON/OFF可）
- 「託すテーマ」を人物に紐付けられる機能（例：「資産はFPの○○さん」「医療は近所の田中さん」）

### D. 診断の分岐対応

現在は全員一律。v7.5では冒頭で：
- 家族構成（既婚/未婚、子の有無）
- 近くに頼れる家族の有無
- 性別役割への意識

をヒアリングし、各テーマの問いを微分岐させる。

### E. 「学ぶ」レイヤーの構造解説コンテンツ

LP内に**構造解説（COTEN型）の記事スペース**が必要：
- 「なぜ女性に介護が偏ってきたか（歴史的経緯）」
- 「2040年問題と単身世帯化の構造」
- 「家族モデルは歴史的構築物である」

実装案：LP内に「Reading（読み物）」セクション追加、または別ビュー `view-reading` 新設。

### F. AIナビゲーターのスクリプト更新

`CHAT_SCENARIOS` を v7.5 マニフェスト準拠に更新：
- 「家族と話す前に考えておくこと」→「家族／友人／専門家／自分自身と話す前に」
- 既婚前提の問いかけを分岐対応
- 「専門家と賢く繋がる」視点を選択肢に追加

### G. 安心デザインカード（PDF出力）

家系図には印刷機能あり。これを発展させて：
- 診断結果＋関係性マップ＋優先テーマ＋連携先メモ を1枚にまとめたPDF
- 家族・士業・行政共有用

## 技術的論点・要判断事項

### 1. クリプト/シードフレーズ託しは「実装するか／教育のみか」

**懸念**：実機能としてシードフレーズや秘密鍵をDBに保存するのは、たとえ暗号化しても重大なセキュリティ・法的リスク。
**推奨**：Phase 1では**教育コンテンツ＋テンプレ提供のみ**。実物の管理は「Hardware Wallet＋分散保管」を推奨し、TDN側は「どこに何があるかのメモ」「遺族への伝え方ガイド」までに留める。

### 2. ビルドステップ導入の是非

**現状**：ビルドなし、CDNでSupabase読込、Vercelに直デプロイ。
**判断**：Phase 1は現状維持を推奨。LLM接続やテスト導入時に Vite/Next.js 等を検討。今のシンプルさは強み。

### 3. ファイル分割

**現状**：`family.js` が 868行、`app.js` が 712行と肥大化傾向。
**判断**：Phase 1の新機能追加で限界に近づく。**Phase 1の終盤**で：
- `app.js` → `themes.js`(データ) ＋ `diagnosis.js`(ロジック) ＋ `chat.js`(モック) に分割
- `family.js` → `family-state.js` ＋ `family-render.js` ＋ `family-layout.js` に分割

### 4. ChibatechHomeWork配下にプロジェクトが同居している件

**現状**：`5_prototype_v2/` は授業課題リポジトリ `ChibatechHomeWork` の中。
**判断**：プロトタイプ段階では問題なし。本格運用フェーズで独立リポジトリへの切り出しを検討（Phase 3以降）。

### 5. anon キーがソースに書かれている件

**現状**：`supabase-config.js` に anon key 直書き。
**判断**：これは正しい運用。anon key は公開前提のキーで、データはRLSで守る。問題なし。

### 6. 診断結果・チャット内容を保存するか

**論点**：保存することでユーザーが「進捗を残せる」価値が出る。一方で、デジタル遺品の意思表示など機微情報の管理責任が増す。
**推奨**：Phase 1で**診断履歴は保存**、チャット履歴は保存しない（モックだから）。Phase 2でLLM接続時に再検討。
